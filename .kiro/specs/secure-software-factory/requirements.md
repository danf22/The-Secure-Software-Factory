# Requirements Document

## Introduction

The Secure Software Factory is a production-grade DevSecOps pipeline for a fintech treasury and FX platform operating in the Mexico-US corridor. The organization is in the process of IFPE authorization with CNBV/Banxico and advancing toward SOC 2 compliance. With ~25 engineers across 5 SWAT teams deploying continuously (Lead Time < 1 hour), this system embeds automatic security guardrails into the CI/CD pipeline without degrading developer velocity. The factory wraps a representative vulnerable seed application in multi-layer security scanning, policy-as-code gates, and supply-chain evidence generation, producing auditable artifacts mapped to IFPE and SOC 2 controls.

## Glossary

- **Pipeline**: The GitHub Actions CI/CD workflow that orchestrates all security scanning layers, policy gates, and artifact generation
- **Vulnerable_Seed**: A deliberately insecure Python/FastAPI microservice with its Dockerfile and Terraform infrastructure, designed to represent the production stack with known vulnerabilities for demonstration purposes
- **Policy_Gate**: An OPA/Conftest or Checkov-based enforcement point that evaluates scan results against custom business-specific policies and blocks or allows the build
- **SBOM**: Software Bill of Materials generated by Syft, listing all dependencies and their versions for supply-chain transparency
- **SARIF_Report**: Static Analysis Results Interchange Format file aggregating findings from all scanning layers into an auditable evidence artifact
- **Secrets_Scanner**: Gitleaks-based tool that detects hardcoded secrets, API keys, and credentials in source code and git history
- **SAST_Scanner**: Semgrep-based Static Application Security Testing tool that identifies code-level vulnerabilities such as injection flaws
- **SCA_Scanner**: Software Composition Analysis tool (Trivy/Dependabot) that identifies known CVEs in third-party dependencies
- **IaC_Scanner**: Checkov-based Infrastructure-as-Code scanner that detects misconfigurations in Terraform definitions
- **Container_Scanner**: Trivy-based scanner that identifies vulnerabilities and misconfigurations in Docker images
- **Waiver**: A documented, time-bound exception to a policy gate failure, requiring justification and approval before allowing a blocked build to proceed
- **Provenance_Attestation**: A signed record (cosign/SLSA) that cryptographically proves the origin, build process, and integrity of a container image
- **Threat_Model**: A structured analysis of threats to the service and pipeline, covering supply-chain attacks, insider threats, and external adversaries
- **ADR**: Architecture Decision Record documenting the rationale, trade-offs, and alternatives considered for each tooling and design choice
- **Red_Demo**: A pipeline execution where the Vulnerable_Seed triggers policy gate failures, demonstrating that insecure code is blocked from progressing
- **Green_Demo**: A pipeline execution where remediated code passes all policy gates, demonstrating the secure path to production

## Requirements

### Requirement 1: Vulnerable Seed Application

**User Story:** As a security engineer, I want a representative vulnerable microservice that mimics the stack, so that I can demonstrate and validate each layer of the security pipeline against realistic flaws.

#### Acceptance Criteria

1. THE Vulnerable_Seed SHALL include a Python/FastAPI microservice containing at least one hardcoded secret, one dependency with a known CVE, and one injection vulnerability
2. THE Vulnerable_Seed SHALL include a Dockerfile that runs the application as the root user
3. THE Vulnerable_Seed SHALL include Terraform definitions containing a public S3 bucket without encryption at rest, an IAM policy with wildcard actions, and a security group open to 0.0.0.0/0
4. WHEN the Vulnerable_Seed is scanned by each Pipeline layer, THE Pipeline SHALL detect at least one finding per layer (secrets, SAST, SCA, IaC, container)

### Requirement 2: Multi-Layer Security Pipeline

**User Story:** As a platform engineer, I want a CI/CD pipeline with multiple security scanning layers, so that vulnerabilities are detected through defense-in-depth rather than relying on a single scanner.

#### Acceptance Criteria

1. THE Pipeline SHALL execute the following scanning layers in sequence: Secrets_Scanner, SAST_Scanner, SCA_Scanner, IaC_Scanner, Container_Scanner
2. WHEN a commit is pushed to the repository, THE Pipeline SHALL trigger automatically and execute all scanning layers
3. THE Pipeline SHALL complete all scanning layers within 10 minutes for the Vulnerable_Seed application
4. WHEN any scanning layer produces findings, THE Pipeline SHALL record the findings in SARIF format
5. THE Pipeline SHALL execute each scanning layer independently so that a failure in one layer does not prevent other layers from completing

### Requirement 3: Policy-as-Code Gate

**User Story:** As a compliance officer, I want custom business-specific policies that enforce security standards, so that violations specific to our regulatory environment are automatically blocked.

#### Acceptance Criteria

1. THE Policy_Gate SHALL enforce the following custom policies: no unencrypted storage at rest, no IAM policies with wildcard actions, no containers running as root, no security groups open to 0.0.0.0/0
2. WHEN any custom policy is violated, THE Policy_Gate SHALL fail the build and output a human-readable explanation identifying the violated policy and the offending resource
3. THE Policy_Gate SHALL use OPA/Conftest or Checkov custom checks to evaluate policies, not relying solely on default scanner rules
4. WHEN a valid Waiver is associated with a policy violation, THE Policy_Gate SHALL allow the build to proceed and log the waiver justification
5. THE Policy_Gate SHALL evaluate all policies before reporting results, providing a complete list of violations rather than stopping at the first failure

### Requirement 4: Supply Chain Evidence and Integrity

**User Story:** As an auditor, I want cryptographically verifiable evidence of build provenance and a complete dependency inventory, so that I can verify the integrity and origin of every deployed artifact.

#### Acceptance Criteria

1. WHEN the Pipeline builds a container image, THE Pipeline SHALL generate an SBOM using Syft containing all OS packages and application dependencies
2. WHEN the Pipeline produces a container image, THE Pipeline SHALL sign the image using cosign and attach a Provenance_Attestation
3. THE SBOM SHALL be stored as a build artifact accessible for audit review
4. WHEN a signed image is verified, THE Provenance_Attestation SHALL confirm the image was built by the Pipeline from the expected source repository and commit

### Requirement 5: Red and Green Demonstration

**User Story:** As a stakeholder, I want clear evidence that the pipeline blocks insecure code and allows secure code, so that I can trust the factory enforces security standards.

#### Acceptance Criteria

1. WHEN the Vulnerable_Seed is submitted to the Pipeline without remediation, THE Policy_Gate SHALL fail the build and produce a Red_Demo report listing all violations
2. WHEN remediated code addressing all policy violations is submitted to the Pipeline, THE Policy_Gate SHALL pass the build and produce a Green_Demo report confirming compliance
3. THE Red_Demo SHALL demonstrate at least one blocked finding from each scanning layer (secrets, SAST, SCA, IaC, container)
4. THE Green_Demo SHALL demonstrate that all custom policy violations have been resolved

### Requirement 6: Threat Model

**User Story:** As a security architect, I want a structured threat model covering the service and pipeline, so that supply-chain risks and attack vectors are documented and mitigated.

#### Acceptance Criteria

1. THE Threat_Model SHALL identify threats across the following categories: supply-chain attacks on dependencies, compromised build environment, insider threats, and external adversaries targeting the service
2. THE Threat_Model SHALL map each identified threat to the Pipeline layer or control that mitigates the threat
3. THE Threat_Model SHALL document residual risks for threats that are not fully mitigated by the current Pipeline configuration

### Requirement 7: Architecture Decision Records

**User Story:** As a technical lead, I want documented rationale for each tooling choice, so that trade-offs (OSS vs managed, false-positive rates, performance impact) are transparent and reviewable.

#### Acceptance Criteria

1. THE ADR collection SHALL include a decision record for each scanning tool selected (Gitleaks, Semgrep, Trivy, Checkov, Syft, cosign)
2. WHEN an ADR is created, THE ADR SHALL document the context, decision, alternatives considered, and trade-offs including false-positive management strategy
3. THE ADR collection SHALL include a decision record justifying the choice between OSS and managed/commercial alternatives for each category

### Requirement 8: Regulatory Mapping

**User Story:** As a compliance officer, I want pipeline controls mapped to CNBV/IFPE and SOC 2 requirements, so that audit evidence directly supports our regulatory authorization process.

#### Acceptance Criteria

1. THE Pipeline SHALL produce a mapping document linking each scanning layer and Policy_Gate check to the corresponding CNBV/IFPE control requirement
2. THE Pipeline SHALL produce a mapping document linking each scanning layer and Policy_Gate check to the corresponding SOC 2 Trust Services Criteria
3. WHEN the Pipeline completes a run, THE SARIF_Report SHALL include metadata tags referencing the applicable regulatory controls for each finding

### Requirement 9: Gradual Rollout to Engineering Teams

**User Story:** As an engineering manager, I want a rollout plan that introduces security gates gradually across 5 squads, so that teams adopt secure practices without disrupting their current deployment velocity.

#### Acceptance Criteria

1. THE Pipeline SHALL support a phased enforcement mode where policy violations generate warnings without blocking builds during the onboarding period
2. THE Pipeline SHALL support per-team configuration allowing different squads to be at different enforcement levels simultaneously
3. WHEN a team transitions from warning mode to enforcement mode, THE Pipeline SHALL notify the team at least 5 business days before enforcement begins
4. THE Waiver workflow SHALL require a justification, an approver, and an expiration date for each exception granted
5. THE Pipeline SHALL provide a developer experience dashboard showing scan results, violation trends, and remediation guidance per team

### Requirement 10: Auditability and Evidence Retention

**User Story:** As an auditor, I want all security scan results and policy decisions retained as immutable evidence, so that I can reconstruct the security posture of any deployment at any point in time.

#### Acceptance Criteria

1. THE Pipeline SHALL store all SARIF_Reports, SBOMs, and Policy_Gate decisions as immutable build artifacts for a minimum retention period of 2 years
2. WHEN a Waiver is granted, THE Pipeline SHALL record the waiver justification, approver identity, expiration date, and associated policy violation in the audit trail
3. THE Pipeline SHALL generate a per-run summary report linking the commit SHA, all scan findings, policy decisions, and resulting build status into a single auditable record

### Requirement 11: Pre-commit Security Hooks

**User Story:** As a developer, I want fast security feedback before I push code, so that I catch secrets and basic issues at my workstation without waiting for the full pipeline.

#### Acceptance Criteria

1. THE Pipeline SHALL provide installable pre-commit hooks that run Secrets_Scanner and basic SAST_Scanner checks locally
2. WHEN a pre-commit hook detects a secret, THE hook SHALL block the commit and display the file and line containing the secret
3. THE pre-commit hooks SHALL complete execution within 30 seconds for a typical changeset of fewer than 50 files

### Requirement 12: Documentation and README

**User Story:** As an evaluator, I want a comprehensive README documenting the architecture, usage, and evidence, so that I can assess the system without additional walkthroughs.

#### Acceptance Criteria

1. THE README SHALL include an architecture diagram showing all Pipeline layers, their interactions, and the flow from commit to deployment
2. THE README SHALL include instructions for reproducing the Red_Demo and Green_Demo locally or in CI
3. THE README SHALL reference all ADRs, the Threat_Model, and the regulatory mapping documents
4. THE README SHALL include a cost estimation for running the security stack in production at scale
